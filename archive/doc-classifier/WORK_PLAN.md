# doc-classifier 1.0 기획서

- 작성일: 2026-10-27 (9절 사용자 회신 반영해 확정). 진행: 0~4단계 구현 완료(0.9.0), 5단계 Windows 실기 대기
- 목적: Windows 11에서 지정한 폴더(하위 전체)의 파일을 **목록화 -> 파일명으로 분류 -> 표본만 살짝 읽어 확인**하는 CLI 도구. OpenCode 스킬로 26B~30B 경량 LLM이 호출합니다.
- 규모 전제: 집 PC 약 30GB, **회사 PC 약 12TB 로컬 디스크** (파일 수 수백만~수천만 개 가능). 이 디스크는 **네트워크로 공유 중**이라 다른 사람이 동시에 쓰고 있습니다. 한 번에 다 읽으면 PC가 멈추고 공유 사용자도 느려지므로, 단계마다 비용을 제한하는 것이 설계의 중심입니다.
- 실행 환경: 회사 PC에 WinPython 폴더를 그대로 복사해 사용 (설치 없음). 도구는 공유 경로(UNC)가 아니라 **그 PC에서 로컬 경로(`D:\...`)로** 실행합니다.

## 1. 설계 원칙

| # | 원칙 | 이유 |
|---|---|---|
| P1 | **단계를 나눈다**: 목록(파일을 열지 않음) -> 분류(이름만) -> 확인(표본만, 앞부분만) | 12TB 전체 내용을 읽는 것은 불가능. 비싼 단계일수록 대상 수를 줄인다 |
| P2 | **메모리는 파일 수와 무관하게 일정**: 결과는 SQLite 파일(`sqlite3`, 표준 라이브러리)에 묶음 단위로 기록하고, 목록을 메모리에 쌓지 않는다 | 수천만 행을 리스트/DataFrame으로 들면 메모리 부족 |
| P3 | **언제 끊겨도 이어서 한다**: 폴더 단위로 진행 상태를 기록하고 `--resume`으로 이어서 실행 | 12TB 목록화는 수십 분~수 시간. 중단(Ctrl+C, 절전, 오류)이 정상 시나리오 |
| P4 | **원본은 절대 바꾸지 않는다**: 읽기 전용으로만 열고, 이동/이름변경/삭제 기능은 1.0에 없음. Office COM도 쓰지 않음(앱을 띄우지 않음) | 사용자 자료 보호. 정리(이동)는 결과를 사람이 확인한 뒤의 별도 단계 |
| P5 | **PC와 공유 사용자를 방해하지 않는다**: 프로세스 우선순위와 I/O 우선순위를 낮추고(백그라운드 모드), 확인 단계는 파일당 시간·크기 상한. 파일은 다른 프로세스의 읽기·쓰기를 막지 않는 방식으로만 연다 | 업무 중, 공유 중에 실행해도 체감 속도 저하와 파일 잠금이 없어야 함. Python `open`, `zipfile`(docx/xlsx/pptx), `pymupdf`는 읽는 동안에도 다른 프로세스가 쓸 수 있음을 집 PC에서 확인 |
| P6 | **열면 안 되는 파일은 목록 단계에서 걸러 둔다**: 클라우드 자리표시자(OneDrive 등 열면 내려받기 시작), 오프라인 파일, 정션/심볼릭 링크(무한 반복), 시스템 폴더 | 한 번 잘못 열면 수 TB 다운로드나 무한 루프 |
| P7 | 저장소 ACI 계약: stdout 1줄 JSON, exit 0/1/2/130, `VERIFIED:`/`STOP_RETRY:`/`ERROR:`, 로그 태그 | `AGENTS.md`, `CLI/README.md` |
| P8 | 판단은 도구가, LLM은 명령 1회 + 요약 JSON만 | 경량 LLM. 수백만 행 결과를 LLM에 넣지 않고 집계·표본·파일 경로만 준다 |

## 2. 전체 흐름

```text
[1] scan      폴더 트리 목록화 (파일을 열지 않음: 이름, 확장자, 크기, 수정일, 속성)      -> <작업>.db
[2] classify  파일명/확장자/폴더명 규칙으로 분류 (디스크 I/O 없음, DB만 읽고 씀)        -> 같은 DB에 category 기록
[3] peek      분류별 표본만 앞부분을 읽어 분류가 맞는지 확인 (파일당 시간/크기 상한)     -> confirmed / changed / unreadable
[4] summary   분류별 개수·용량·예시, 확인 결과, 다음 명령                                -> JSON + 선택적으로 xlsx/csv/md 보고서
    list      조건(분류, 확장자, 기간, 폴더)으로 파일 목록 조회 (페이지 단위)
```

- 단계마다 독립 실행. `classify`는 규칙을 바꿔 여러 번 다시 돌려도 디스크를 읽지 않으므로 빠름.
- 결과 DB 하나가 "작업" 단위: `data\<작업이름>.db` (기본 이름은 대상 폴더명 + 날짜).

## 3. 단계별 설계

### 3.1 scan (목록화)

| 항목 | 설계 |
|---|---|
| 순회 | `os.scandir` 반복(스택) 순회. 재귀 함수 쓰지 않음(깊은 트리에서 스택 초과 방지). Windows에서 `DirEntry.stat()`은 디렉터리 읽기 결과를 재사용하므로 **파일마다 추가 디스크 접근이 없음** |
| 기록 항목 | 경로(폴더 id + 파일명), 확장자, 크기, 수정일, 만든 날짜, 파일 속성(숨김/시스템/읽기전용/오프라인/자리표시자/재분석 지점) |
| 저장 | SQLite (WAL 모드), 5,000행 단위 묶음 기록. 폴더 경로는 `dirs` 테이블로 따로 두어 DB 크기 절감 |
| 건너뜀 | 정션·심볼릭 링크(재분석 지점) 폴더, `$Recycle.Bin`, `System Volume Information`, `Windows`, 설정한 제외 패턴(`--exclude`). 건너뛴 폴더와 이유는 DB에 기록 |
| 위험 파일 표시 | 클라우드 자리표시자(`RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN`), `OFFLINE` 속성은 목록에는 넣되 `no_read` 표시 -> peek에서 절대 열지 않음 |
| 긴 경로 | 260자 초과 경로는 `\\?\` 접두어로 처리 |
| 오류 | 권한 없음/경로 없음/네트워크 끊김은 폴더 단위로 기록하고 계속 진행. 오류 폴더 수와 예시를 결과에 포함 |
| 중단/재개 | 폴더를 다 읽으면 `done` 표시. `--resume`은 `done`이 아닌 폴더부터 다시. Ctrl+C면 기록을 마무리하고 exit 130 + 재개 명령을 `next_commands`로 |
| 부하 제한 | 백그라운드 우선순위(`PROCESS_MODE_BACKGROUND_BEGIN`, pywin32), `--max-files`, `--max-depth`, `--time-limit`(초과 시 중단하고 재개 명령 제공), 네트워크 드라이브는 `--throttle-ms`(폴더 사이 쉬기) |
| 다시 스캔 | 같은 작업 DB에 다시 실행하면 바뀐 폴더만 갱신(폴더 수정 시각 비교)하는 증분 모드는 1.1 후보 |
| 진행 로그 | stderr에 `[PROGRESS] 폴더 N개, 파일 M개, X GB, 초당 K개` 를 일정 간격으로 (에이전트 무응답 타임아웃 방지) |

### 3.2 classify (파일명 기반 분류)

디스크를 읽지 않고 DB의 이름 정보만 씁니다. 결과에 **근거(어느 키워드가 어디서 맞았는지)** 가 남습니다.

#### 분류 규칙 파일 (사용자 결정: JSON)

카테고리 이름과 키워드 목록만 주는 단순한 형식입니다. 경량 LLM이나 사람이 바로 고칠 수 있습니다.

```json
{
  "계약서": ["OOO계약", "기안", "기획"],
  "도면": [".dwg", ".dxf"]
}
```

| 규칙 | 내용 |
|---|---|
| 키워드 종류 | `.`으로 시작하면 **확장자** (정확히 일치, `.dwg`). 그 외는 **글자 포함** 키워드 |
| 비교 방식 | 대소문자 무시, 한글 정규화(NFC: 맥에서 온 파일명의 자모 분리 대비), 공백·`_`·`-` 차이 무시(`시험 성적서` = `시험_성적서` = `시험성적서`) |
| 어디서 찾나 | 파일명(확장자 제외)과 상위 폴더 이름들. 파일명에서 맞으면 점수 높게, 폴더명에서 맞으면 낮게(가까운 폴더일수록 높게) |
| 점수 | 확장자 3점, 파일명 키워드 2점, 바로 위 폴더 1점, 더 위 폴더 0.5점. 같은 카테고리 안의 여러 키워드는 합산 |
| 여러 카테고리가 맞을 때 | 점수 1위가 `category`. 동점이면 **JSON에 먼저 적은 카테고리** 우선(작성 순서 = 우선순위). 맞은 카테고리 전체와 점수는 `matches`에 기록 |
| 신뢰도 | 1위와 2위 점수 차로 `high` / `medium` / `low`. 아무것도 안 맞으면 `미분류` |
| 검증 | 파일을 읽을 때 형식 오류(JSON 문법, 빈 목록, 키워드가 문자열이 아님)는 위치를 짚어 `STOP_RETRY`. 너무 짧은 키워드(1글자)는 `[WARN]`(오분류 위험) |
| 예시 파일 | `rules.example.json` (기본 카테고리 예시). 1.1에서 `{"계약서": {"keywords": [...], "exclude": [...]}}` 같은 확장 형식을 받을 수 있게 키 형태를 열어 둠 |

- 규칙을 바꾸면 `classify`만 다시 실행합니다 (수백만 행도 DB 안에서 처리, 디스크 접근 없음). 결과에 카테고리별 개수와 "가장 많이 맞은 키워드", "미분류 파일명에 자주 나오는 단어"를 넣어 규칙 보완을 돕습니다.

#### 함께 기록하는 보조 정보 (규칙과 무관, 내장)

| 항목 | 내용 |
|---|---|
| 형식 (`kind`) | 확장자로 정하는 파일 형식: 문서, 표, 발표, PDF, 한글, 메일, 이미지, 도면, 압축, 코드/데이터, 미디어, 실행파일, 임시/시스템, 기타. peek에서 어떤 방식으로 읽을지 정하는 데도 씀 |
| 이름 속 정보 | 날짜(`20260301`, `2026-03`, `26년 3월`), 버전(`v2`, `rev3`, `최종`, `최최종`), 사본 표시(`- 복사본`, `(1)`), 임시 파일(`~$`, `.tmp`) |
| 중복 후보 | 같은 이름 + 같은 크기 묶음 (내용 해시는 비싸므로 1.0에서는 하지 않음) |

- 1.1 후보: peek으로 확인된 결과를 학습 데이터로 삼아 파일명 문자 n-gram 분류기(scikit-learn)로 규칙이 놓친 것을 보완.

### 3.3 peek (살짝 읽어 확인)

| 항목 | 설계 |
|---|---|
| 대상 | 전체가 아니라 **분류별 표본** (기본: 분류마다 20개, `--per-category`, `--max-files` 전체 상한). `low` 신뢰도와 `미분류`를 우선 포함 |
| 읽는 양 | 파일 앞부분만. PDF 첫 1~2쪽 텍스트, DOCX 앞 단락 20개, PPTX 슬라이드 제목, XLSX 시트 이름 + 첫 10행(읽기 전용 모드), HWP 5.0은 미리보기 텍스트(`PrvText` 스트림, 본문 해석 없이 빠름), HWPX는 `Preview/PrvText.txt`, TXT/CSV/MD 앞 8KB, EML 헤더와 본문 앞부분 |
| 상한 | 파일당 크기 상한(기본 200MB 초과면 열지 않음), **파일당 시간 상한**(기본 10초): 별도 작업 프로세스에서 읽고 시간을 넘기면 그 프로세스를 끝내고 다음 파일로. 깨진 파일이나 거대한 PDF가 전체를 멈추지 못하게 함 |
| 열지 않음 | `no_read`(클라우드 자리표시자, 오프라인), 실행 파일, 압축 파일(1.0은 안을 보지 않음) |
| DRM | 회사 PC에서는 DRM 문서를 python-docx, python-pptx, openpyxl, pandas, pymupdf로 바로 읽을 수 있음(사용자 확인). 그래서 Office 연계 없이 라이브러리로 읽습니다. 그래도 파일 앞부분 서명이 형식과 다르면(zip/OLE/PDF가 아님) `encrypted_or_drm`으로 기록하고 넘어감(HWP, 다른 보호 방식 대비) |
| 판정 | 같은 규칙 JSON의 키워드로 확인: 읽은 텍스트에 그 카테고리의 키워드가 있으면 `confirmed`, 다른 카테고리 키워드가 더 많으면 `changed`(새 카테고리 제안), 텍스트가 없으면 `no_text`(스캔 PDF 등), 실패는 `unreadable` + 이유. 확장자 키워드만 있는 카테고리(예: 도면)는 형식이 맞으면 `confirmed` |
| 기록 | 판정, 짧은 발췌(200자), 읽은 시간. 원문 전체는 저장하지 않음(DB 크기와 보안) |
| 결과 | 분류별 확인율(confirmed / 표본 수). 확인율이 낮은 분류는 규칙 보완 대상으로 `recommendations`에 |
| 재사용 | PDF는 `import pymupdf`(옛 이름 `fitz`는 사용 중단 예정). 파서는 office-cli `reader.py`의 검증된 코드(HWP 제어문자, PPTX 순서 등)를 "앞부분만 읽기"로 줄여 이 폴더에 둡니다. 도구 폴더는 단독 배포 가능해야 하므로 다른 도구를 import하지 않음 |

### 3.4 summary / list

- `summary`: 형식별·분류별 개수와 용량, 상위 폴더별 분포, 확인율, 오류/건너뜀 요약, 중복 후보 수, 오래된 파일 비율. JSON은 상위 N개로 잘라 LLM에 맞는 크기 유지(`truncated` + 이어보기 명령).
- `--save 보고서.xlsx` (사용자 결정: 결과는 엑셀): 시트는 `요약`(카테고리별 개수·용량·확인율), `카테고리별`(카테고리마다 상위 폴더 분포), `확인 결과`(peek 표본과 판정·발췌), `미분류 단어`(규칙 보완용), `오류·건너뜀`, `파일 목록`. openpyxl 쓰기 전용 모드로 메모리 일정하게 저장.
  - 파일 목록이 한 시트 한도(1,048,576행)를 넘으면 `파일 목록 2`, `3`...으로 나누고, 그래도 너무 크면(기본 300만 행 초과) 목록만 csv로 따로 저장하고 엑셀에는 요약만 둡니다.
- `list`: `--category 회의록 --ext hwp --since 2025-01 --folder ...` 조건 조회, 페이지 단위(`--page`, 기본 100행). 결과 경로를 office-cli `reader.py read`나 다른 도구로 넘길 수 있게 `next_commands` 제공.

## 4. 명령 체계 (초안)

진입점 1개, 동사형 하위 명령 (office-cli와 같은 방식).

```bat
python doc_classifier.py scan     --root "D:\자료" [--job 이름] [--exclude "*\node_modules\*"] [--max-depth N] [--time-limit 3600] [--resume]
python doc_classifier.py classify --job 이름 --rules rules.json
python doc_classifier.py peek     --job 이름 [--per-category 20] [--max-files 500] [--timeout 10]
python doc_classifier.py summary  --job 이름 [--save 보고서.xlsx]
python doc_classifier.py list     --job 이름 --category 회의록 [--ext hwp] [--since 2025-01] [--page 2]
python doc_classifier.py jobs                                            :: 작업(DB) 목록과 진행 상태
```

- 결과 JSON 공통: `job`, `db_file`, `counts`, `next_commands`(바로 실행 가능한 다음 단계; 자리표시자가 있으면 `needs_input: true`, ml-kit 2.1.1과 같은 규칙).
- 큰 작업의 예상: `scan` 결과에 파일 수·용량과 함께 "peek 예상 시간"을 넣어 LLM이 사용자에게 먼저 알릴 수 있게 함.

## 5. 폴더 구성

```text
CLI/doc-classifier/
├── SKILL.md            # OpenCode 스킬 (name: doc-classifier)
├── README.md           # 사람용 설명서
├── CHANGELOG.md        # 1.0.0부터 + 남은 할 일
├── WORK_PLAN.md        # 이 문서
├── requirements.txt    # pywin32, pymupdf, olefile, openpyxl, python-docx, python-pptx (모두 표준 환경, WinPython 복사본에 포함)
├── doc_classifier.py   # 진입점 (scan / classify / peek / summary / list / jobs)
├── _dc_runtime.py      # 응답 계약, 로그, 경로 (office-cli 것과 같은 계약, 단독 배포를 위해 복사)
├── _dc_store.py        # SQLite 스키마, 묶음 기록, 진행 상태, 작업 잠금
├── _dc_scan.py         # 목록화: 폴더 대기열(DB), 속성/링크/클라우드 판정, 우선순위, 상한
├── _dc_rules.py        # 규칙 JSON 읽기·검증, 키워드 정규화, 점수 계산, 형식(kind) 표
├── _dc_peek.py         # 형식별 "앞부분만" 읽기 + 작업 프로세스/시간 상한
├── rules.example.json  # 분류 규칙 예시 ({"카테고리": ["키워드", ".확장자"]})
├── tools/run_win_tests.py   # Windows 실기 테스트 (대용량 트리, 자리표시자, 정션, 긴 경로, 잠긴 파일)
└── tests/              # 오프라인 테스트 (가짜 트리 생성기 포함)
```
- 내부 모듈은 `_dc_` 접두어: 저장소 pytest가 한 세션에서 모든 도구를 돌리므로 office-cli의 `_runtime` 등과 이름이 겹치지 않게 합니다.

## 6. 진행 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| 0 | 폴더, `_dc_runtime.py`, SQLite 스키마, `jobs`, 계약 테스트 | pytest. **완료 (0.1.0)** |
| 1 | `scan`: 순회, 속성 기록, 제외 규칙, 중단/재개, 우선순위 낮추기 | 가짜 트리 10만 파일(속도·메모리), 권한 오류, 긴 경로, 재개. **완료 (0.1.0)**: 집 PC 실기 9/9 통과, 결과는 CHANGELOG |
| 2 | `classify`: 규칙 JSON 읽기·검증, 키워드 정규화, 점수와 우선순위, 형식 표, 날짜/버전/사본 추출 | 규칙 단위 테스트(확장자/포함/폴더/동점/미분류/잘못된 JSON), 한글 파일명 사례 모음(NFD, 공백 변형). **완료 (0.9.0)** |
| 3 | `peek`: 형식별 앞부분 읽기, 작업 프로세스 시간 상한, DRM/암호 판별, 판정 | 실제 샘플 파일(pdf/docx/pptx/xlsx/hwp/hwpx/eml), 깨진 파일, 거대 파일, 무한 대기 파일. **완료 (0.9.0)** |
| 4 | `summary`, `list`, 보고서 저장, SKILL/README/CHANGELOG | 계약 테스트, LLM 크기 상한. **완료 (0.9.0)** |
| 5 | Windows 실기 러너: 대용량 가짜 트리(수십만 파일), OneDrive 자리표시자, 정션 루프, 260자 초과 경로, 잠긴 파일, 네트워크 드라이브(가능하면) | 집 PC -> 회사 PC 순서. S1~S9 통과(0.1.0), S10~S15 러너 준비됨(0.9.0) -> 실기 대기 |

- 1~4단계는 클라우드(Linux)에서 개발·테스트 가능. Windows 전용 부분(파일 속성, 우선순위, 자리표시자, `\\?\`)은 Linux에서는 건너뛰도록 분기하고 5단계 실기에서 확인.
- 성능 목표는 실기에서 측정 후 확정(예: 로컬 SSD에서 목록화 초당 수만 개, 메모리 200MB 이하 유지).
- 집 PC 측정(0.1.0): 실제 C:\ 초당 약 1.1만 개, 메모리 20~32MB, DB 파일당 약 114바이트. 12TB에 파일 2천만 개라면 목록화 약 30분~1시간, DB 약 2.3GB로 추정(회사 PC에서 확인).

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 12TB 순회 중 메모리 부족 | DB 묶음 기록, 메모리 일정(P2). 실기에서 수십만 파일로 메모리 측정 |
| 클라우드 자리표시자를 열어 대량 다운로드 | 목록 단계에서 속성으로 표시, peek에서 절대 열지 않음(P6). 실기 테스트 항목 |
| 깨진/거대 파일에서 멈춤 | 작업 프로세스 + 파일당 시간 상한, 크기 상한 |
| 백신 실시간 검사로 peek가 느려짐 | 표본 수 상한, 진행 로그, `--time-limit` |
| 업무 중 PC 느려짐, 공유 사용자 방해 | 백그라운드 프로세스·I/O 우선순위, 로컬 경로로 실행, 다른 프로세스를 막지 않는 읽기 방식, peek 표본 상한. 실기에서 "공유 폴더 파일을 다른 PC가 쓰는 중에 peek" 확인 |
| 마지막 접근 시각 변경 | peek가 파일을 열면 NTFS 마지막 접근 시각이 바뀔 수 있음(대용량 볼륨은 Windows가 보통 갱신을 끔). 수정 시각·내용은 바뀌지 않음. README에 명시 |
| 결과 DB가 커짐 | 폴더 경로 분리 저장, 발췌는 200자, 원문 저장 안 함. 1천만 파일 기준 DB 크기 실측 |
| 민감 정보 노출 | 발췌는 짧게, DB는 `data` 폴더에만, LLM에는 집계·경로·짧은 발췌만 |
