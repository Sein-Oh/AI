# doc-classifier 1.0 기획서

- 작성일: 2026-10-27 (초안, "9. 결정 필요" 회신 후 확정)
- 목적: Windows 11에서 지정한 폴더(하위 전체)의 파일을 **목록화 -> 파일명으로 분류 -> 표본만 살짝 읽어 확인**하는 CLI 도구. OpenCode 스킬로 26B~30B 경량 LLM이 호출합니다.
- 규모 전제: 집 PC 약 30GB, **회사 PC 약 12TB** (파일 수 수백만~수천만 개 가능). 한 번에 다 읽으면 PC가 멈추므로, 단계마다 비용을 제한하는 것이 설계의 중심입니다.

---

## 1. 설계 원칙

| # | 원칙 | 이유 |
|---|---|---|
| P1 | **단계를 나눈다**: 목록(파일을 열지 않음) -> 분류(이름만) -> 확인(표본만, 앞부분만) | 12TB 전체 내용을 읽는 것은 불가능. 비싼 단계일수록 대상 수를 줄인다 |
| P2 | **메모리는 파일 수와 무관하게 일정**: 결과는 SQLite 파일(`sqlite3`, 표준 라이브러리)에 묶음 단위로 기록하고, 목록을 메모리에 쌓지 않는다 | 수천만 행을 리스트/DataFrame으로 들면 메모리 부족 |
| P3 | **언제 끊겨도 이어서 한다**: 폴더 단위로 진행 상태를 기록하고 `--resume`으로 이어서 실행 | 12TB 목록화는 수십 분~수 시간. 중단(Ctrl+C, 절전, 오류)이 정상 시나리오 |
| P4 | **원본은 절대 바꾸지 않는다**: 읽기 전용으로만 열고, 이동/이름변경/삭제 기능은 1.0에 없음. Office COM도 쓰지 않음(앱을 띄우지 않음) | 사용자 자료 보호. 정리(이동)는 결과를 사람이 확인한 뒤의 별도 단계 |
| P5 | **PC를 독점하지 않는다**: 프로세스 우선순위와 I/O 우선순위를 낮추고(백그라운드 모드), 확인 단계는 파일당 시간·크기 상한 | 업무 중 실행해도 체감 속도 저하가 없어야 함 |
| P6 | **열면 안 되는 파일은 목록 단계에서 걸러 둔다**: 클라우드 자리표시자(OneDrive 등 열면 내려받기 시작), 오프라인 파일, 정션/심볼릭 링크(무한 반복), 시스템 폴더 | 한 번 잘못 열면 수 TB 다운로드나 무한 루프 |
| P7 | 저장소 ACI 계약: stdout 1줄 JSON, exit 0/1/2/130, `VERIFIED:`/`STOP_RETRY:`/`ERROR:`, 로그 태그 | `AGENTS.md`, `CLI/README.md` |
| P8 | 판단은 도구가, LLM은 명령 1회 + 요약 JSON만 | 경량 LLM. 수백만 행 결과를 LLM에 넣지 않고 집계·표본·파일 경로만 준다 |

## 2. 전체 흐름

```text
[1] scan      폴더 트리 목록화 (파일을 열지 않음: 이름, 확장자, 크기, 수정일, 속성)      -> <작업>.db
[2] classify  파일명/확장자/폴더명 규칙으로 분류 (디스크 I/O 없음, DB만 읽고 씀)        -> 같은 DB에 category 기록
[3] peek      분류별 표본만 앞부분을 읽어 분류가 맞는지 확인 (파일당 시간/크기 상한)     -> confirmed / changed / unreadable
[4] summary   분류별 개수·용량·예시, 확인 결과, 다음 명령                                -> JSON + 선택적으로 xlsx/csv/md 보고서
    list      조건(분류, 확장자, 기간, 폴더)으로 파일 목록 조회 (페이지 단위)
```

- 단계마다 독립 실행. `classify`는 규칙을 바꿔 여러 번 다시 돌려도 디스크를 읽지 않으므로 빠름.
- 결과 DB 하나가 "작업" 단위: `data\<작업이름>.db` (기본 이름은 대상 폴더명 + 날짜).

## 3. 단계별 설계

### 3.1 scan (목록화)

| 항목 | 설계 |
|---|---|
| 순회 | `os.scandir` 반복(스택) 순회. 재귀 함수 쓰지 않음(깊은 트리에서 스택 초과 방지). Windows에서 `DirEntry.stat()`은 디렉터리 읽기 결과를 재사용하므로 **파일마다 추가 디스크 접근이 없음** |
| 기록 항목 | 경로(폴더 id + 파일명), 확장자, 크기, 수정일, 만든 날짜, 파일 속성(숨김/시스템/읽기전용/오프라인/자리표시자/재분석 지점) |
| 저장 | SQLite (WAL 모드), 5,000행 단위 묶음 기록. 폴더 경로는 `dirs` 테이블로 따로 두어 DB 크기 절감 |
| 건너뜀 | 정션·심볼릭 링크(재분석 지점) 폴더, `$Recycle.Bin`, `System Volume Information`, `Windows`, 설정한 제외 패턴(`--exclude`). 건너뛴 폴더와 이유는 DB에 기록 |
| 위험 파일 표시 | 클라우드 자리표시자(`RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN`), `OFFLINE` 속성은 목록에는 넣되 `no_read` 표시 -> peek에서 절대 열지 않음 |
| 긴 경로 | 260자 초과 경로는 `\\?\` 접두어로 처리 |
| 오류 | 권한 없음/경로 없음/네트워크 끊김은 폴더 단위로 기록하고 계속 진행. 오류 폴더 수와 예시를 결과에 포함 |
| 중단/재개 | 폴더를 다 읽으면 `done` 표시. `--resume`은 `done`이 아닌 폴더부터 다시. Ctrl+C면 기록을 마무리하고 exit 130 + 재개 명령을 `next_commands`로 |
| 부하 제한 | 백그라운드 우선순위(`PROCESS_MODE_BACKGROUND_BEGIN`, pywin32), `--max-files`, `--max-depth`, `--time-limit`(초과 시 중단하고 재개 명령 제공), 네트워크 드라이브는 `--throttle-ms`(폴더 사이 쉬기) |
| 다시 스캔 | 같은 작업 DB에 다시 실행하면 바뀐 폴더만 갱신(폴더 수정 시각 비교)하는 증분 모드는 1.1 후보 |
| 진행 로그 | stderr에 `[PROGRESS] 폴더 N개, 파일 M개, X GB, 초당 K개` 를 일정 간격으로 (에이전트 무응답 타임아웃 방지) |

### 3.2 classify (파일명 기반 분류)

디스크를 읽지 않고 DB의 이름 정보만 씁니다. 규칙 기반이라 결과에 **근거(reason)** 가 남습니다.

분류는 두 축입니다.

| 축 | 값 (기본안) | 근거 |
|---|---|---|
| 형식 (`kind`) | 문서(hwp/hwpx/doc/docx/txt/md), 표(xls/xlsx/csv), 발표(ppt/pptx), PDF, 메일(eml/msg), 이미지, 도면(dwg/dxf), 압축, 코드/데이터, 미디어, 실행파일, 임시/시스템, 기타 | 확장자 표 |
| 업무 유형 (`category`) | 보고서, 회의록, 계획서/기획서, 품의/결재, 공문, 계약서, 견적/발주/구매, 정산/비용, 사양서/설계서, 시험/검사 성적서, 매뉴얼/지침, 교육자료, 발표자료, 인사/이력, 데이터/측정값, 미분류 | 파일명 키워드 + 폴더명 키워드 + 형식 |

- 규칙은 `rules.yaml`(PyYAML, 표준 환경)에 둡니다. 사용자가 회사 용어(부서명, 프로젝트 코드, 양식 번호)를 추가할 수 있게 합니다. 기본 규칙은 도구에 내장.
- 점수 방식: 파일명 키워드(가중치 큼) + 상위 폴더명 키워드 + 형식 사전확률. 1위 점수와 2위 차이로 `confidence`(high/medium/low) 계산.
- 부가 정보도 이름에서 추출: 날짜(`20260301`, `2026-03`, `26년 3월`), 버전 표기(`v2`, `rev3`, `최종`, `최최종`), 사본 표시(`- 복사본`, `(1)`), 임시 파일(`~$`, `.tmp`).
- 중복 후보: 같은 이름 + 같은 크기 묶음 (내용 해시는 비싸므로 1.0에서는 하지 않음).
- 규칙을 바꾸면 `classify`만 다시 실행 (수백만 행도 DB 안에서 처리, 디스크 접근 없음).
- 1.1 후보: peek으로 확인된 결과를 학습 데이터로 삼아 파일명 문자 n-gram 분류기(scikit-learn)를 학습해 규칙이 놓친 것을 보완.

### 3.3 peek (살짝 읽어 확인)

| 항목 | 설계 |
|---|---|
| 대상 | 전체가 아니라 **분류별 표본** (기본: 분류마다 20개, `--per-category`, `--max-files` 전체 상한). `low` 신뢰도와 `미분류`를 우선 포함 |
| 읽는 양 | 파일 앞부분만. PDF 첫 1~2쪽 텍스트, DOCX 앞 단락 20개, PPTX 슬라이드 제목, XLSX 시트 이름 + 첫 10행(읽기 전용 모드), HWP 5.0은 미리보기 텍스트(`PrvText` 스트림, 본문 해석 없이 빠름), HWPX는 `Preview/PrvText.txt`, TXT/CSV/MD 앞 8KB, EML 헤더와 본문 앞부분 |
| 상한 | 파일당 크기 상한(기본 200MB 초과면 열지 않음), **파일당 시간 상한**(기본 10초): 별도 작업 프로세스에서 읽고 시간을 넘기면 그 프로세스를 끝내고 다음 파일로. 깨진 파일이나 거대한 PDF가 전체를 멈추지 못하게 함 |
| 열지 않음 | `no_read`(클라우드 자리표시자, 오프라인), 실행 파일, 압축 파일(1.0은 안을 보지 않음) |
| DRM/암호 | 파일 앞부분 서명이 형식과 다르면(zip/OLE/PDF가 아님) `encrypted_or_drm`으로 기록하고 넘어감. Office를 띄워 여는 경로는 1.0에 없음(필요하면 atomic-cli로 안내) |
| 판정 | 읽은 텍스트에 그 분류의 키워드가 있으면 `confirmed`, 다른 분류 키워드가 더 강하면 `changed`(새 분류 제안), 텍스트가 없으면 `no_text`(스캔 PDF 등), 실패는 `unreadable` + 이유 |
| 기록 | 판정, 짧은 발췌(200자), 읽은 시간. 원문 전체는 저장하지 않음(DB 크기와 보안) |
| 결과 | 분류별 확인율(confirmed / 표본 수). 확인율이 낮은 분류는 규칙 보완 대상으로 `recommendations`에 |
| 재사용 | 파서는 atomic-cli `reader.py`의 검증된 코드(HWP 제어문자, PPTX 순서 등)를 "앞부분만 읽기"로 줄여 이 폴더에 둡니다. 도구 폴더는 단독 배포 가능해야 하므로 다른 도구를 import하지 않음 |

### 3.4 summary / list

- `summary`: 형식별·분류별 개수와 용량, 상위 폴더별 분포, 확인율, 오류/건너뜀 요약, 중복 후보 수, 오래된 파일 비율. JSON은 상위 N개로 잘라 LLM에 맞는 크기 유지(`truncated` + 이어보기 명령).
- `--save 보고서.xlsx|csv|md`: 사람용 보고서. xlsx는 시트별(요약, 분류별 목록, 확인 결과, 오류). 수백만 행은 xlsx 한 시트 한도(1,048,576행)를 넘으므로 목록은 csv로 나누어 저장.
- `list`: `--category 회의록 --ext hwp --since 2025-01 --folder ...` 조건 조회, 페이지 단위(`--page`, 기본 100행). 결과 경로를 atomic-cli `reader.py read`나 다른 도구로 넘길 수 있게 `next_commands` 제공.

## 4. 명령 체계 (초안)

진입점 1개, 동사형 하위 명령 (atomic-cli와 같은 방식).

```bat
python doc_classifier.py scan     --root "D:\자료" [--job 이름] [--exclude "*\node_modules\*"] [--max-depth N] [--time-limit 3600] [--resume]
python doc_classifier.py classify --job 이름 [--rules rules.yaml]
python doc_classifier.py peek     --job 이름 [--per-category 20] [--max-files 500] [--timeout 10]
python doc_classifier.py summary  --job 이름 [--save 보고서.xlsx]
python doc_classifier.py list     --job 이름 --category 회의록 [--ext hwp] [--since 2025-01] [--page 2]
python doc_classifier.py jobs                                            :: 작업(DB) 목록과 진행 상태
```

- 결과 JSON 공통: `job`, `db_file`, `counts`, `next_commands`(바로 실행 가능한 다음 단계; 자리표시자가 있으면 `needs_input: true`, ml-kit 2.1.1과 같은 규칙).
- 큰 작업의 예상: `scan` 결과에 파일 수·용량과 함께 "peek 예상 시간"을 넣어 LLM이 사용자에게 먼저 알릴 수 있게 함.

```text

├── tools/run_win_tests.py   # Windows 실기 테스트 (대용량 트리, 자리표시자, 정션, 긴 경로, 잠긴 파일)
└── tests/              # 오프라인 테스트 (가짜 트리 생성기 포함)
```

## 6. 진행 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| 0 | 폴더, `_runtime.py`, SQLite 스키마, `jobs`, 계약 테스트 | pytest |
| 1 | `scan`: 순회, 속성 기록, 제외 규칙, 중단/재개, 우선순위 낮추기 | 가짜 트리 10만 파일(속도·메모리), 권한 오류, 긴 경로, 재개 |
| 2 | `classify`: 형식 표, 기본 업무 유형 규칙, 날짜/버전/사본 추출, rules.yaml | 규칙 단위 테스트, 한글 파일명 사례 모음 |
| 3 | `peek`: 형식별 앞부분 읽기, 작업 프로세스 시간 상한, DRM/암호 판별, 판정 | 실제 샘플 파일(pdf/docx/pptx/xlsx/hwp/hwpx/eml), 깨진 파일, 거대 파일, 무한 대기 파일 |
| 4 | `summary`, `list`, 보고서 저장, SKILL/README/CHANGELOG | 계약 테스트, LLM 크기 상한 |
| 5 | Windows 실기 러너: 대용량 가짜 트리(수십만 파일), OneDrive 자리표시자, 정션 루프, 260자 초과 경로, 잠긴 파일, 네트워크 드라이브(가능하면) | 집 PC -> 회사 PC 순서 |

- 1~4단계는 클라우드(Linux)에서 개발·테스트 가능. Windows 전용 부분(파일 속성, 우선순위, 자리표시자, `\\?\`)은 Linux에서는 건너뛰도록 분기하고 5단계 실기에서 확인.
- 성능 목표는 실기에서 측정 후 확정(예: 로컬 SSD에서 목록화 초당 수만 개, 메모리 200MB 이하 유지).

## 7. 1.0 범위 밖 (후보)

- 파일 이동/폴더 정리, 이름 바꾸기 (결과 확인 후 별도 도구 또는 1.x에서 "계획만 만들기" 방식으로)
- 압축 파일 내부 목록
- 내용 해시 기반 정확한 중복 찾기
- 증분 스캔(바뀐 폴더만)
- 분류 학습 모델(파일명 n-gram), 내용 기반 전체 분류
- DRM 문서를 Office로 열어 확인 (atomic-cli 연계)
- 이미지/스캔 PDF OCR

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 12TB 순회 중 메모리 부족 | DB 묶음 기록, 메모리 일정(P2). 실기에서 수십만 파일로 메모리 측정 |
| 클라우드 자리표시자를 열어 대량 다운로드 | 목록 단계에서 속성으로 표시, peek에서 절대 열지 않음(P6). 실기 테스트 항목 |
| 깨진/거대 파일에서 멈춤 | 작업 프로세스 + 파일당 시간 상한, 크기 상한 |
| 백신 실시간 검사로 peek가 느려짐 | 표본 수 상한, 진행 로그, `--time-limit` |
| 업무 중 PC 느려짐 | 백그라운드 우선순위, 네트워크 드라이브 쉬기 |
| 결과 DB가 커짐 | 폴더 경로 분리 저장, 발췌는 200자, 원문 저장 안 함. 1천만 파일 기준 DB 크기 실측 |
| 민감 정보 노출 | 발췌는 짧게, DB는 `data` 폴더에만, LLM에는 집계·경로·짧은 발췌만 |

## 9. 결정 필요 (사용자 회신)

1. **업무 유형 분류 목록**: 3.2의 기본안(보고서, 회의록, 계획서 ...)으로 시작할지, 회사에서 쓰는 분류(부서/프로젝트/문서 양식)가 따로 있는지.
2. **대상 저장소**: 12TB가 회사 PC 로컬 디스크인지, 네트워크 드라이브(NAS, 공유 폴더)인지. 네트워크라면 순회 속도와 부하 제한 방식이 달라집니다.
3. **결과 형태**: 사람이 볼 최종 결과를 xlsx 보고서로 할지(기본안), 다른 형식이 필요한지.
4. **DRM 문서 비율**: 회사 문서 대부분이 DRM이면 peek가 거의 `encrypted_or_drm`이 됩니다. 이 경우 1.0에서 atomic-cli(Office로 열기) 연계를 앞당길지.
5. **정리(이동) 기능**: 1.0에서 제외(읽기 전용)하는 기본안에 동의하는지.
